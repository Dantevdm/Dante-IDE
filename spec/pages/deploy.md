# Deploy (Ship › Deploy)

Deploy puts the project on DigitalOcean's App Platform and keeps an eye on it: sign in through the browser, let Dante write the app spec, deploy, then watch deployments, health, metrics and logs, with security findings and recommendations for the whole set-up.

## Highlights
- Signing in happens in your own browser, where you're already signed in to DigitalOcean; Dante never sees a password and keeps the sign-in in the Keychain.
- Dante writes `.do/app.yaml` from the code: Dockerfiles, the apps it recognises, plain HTML folders, compose's Postgres and the env examples. You review and commit it; it's what gets deployed.
- When the code is on GitHub, GitLab or Bitbucket, App Platform builds it and every push deploys; otherwise Dante builds the images here and pushes them to your DigitalOcean registry.
- Nothing is made or changed until you confirm the deploy, with the price in front of you.
- Getting in tells a newcomer how to reach the app: whether it wants an API key, a password or single sign-on, and how the first key or admin gets made, each step runnable where it belongs.
- Security and recommendations checks the spec, the Dockerfiles, the live site's headers, and the app's health and alerts.

## Shows
- Not signed in: a DigitalOcean card saying what signing in does and what Dante asks for (App Platform, the registry, metrics, reading databases and creating the dev database a spec asks for), with Sign in with DigitalOcean (Waiting for the browser… until the reply comes, five minutes at most), and the reason in amber when it was cancelled, refused or timed out.
- Before the first deploy: What Dante would deploy, a row per component (service, static site, worker, job) with where its code comes from, its folder, port and size (static sites say Free), and each database; where the code comes from overall and what was decided, sentence by sentence; anything it couldn't place in amber (an app without a Dockerfile when building here, a database engine App Platform has no dev database for); the region picker; Write .do/app.yaml. Once the file exists the card is The app spec, read from it, with Open .do/app.yaml. Signed in, Use an existing app lists the account's apps.
- The deploy wizard (an 860×640 sheet): a rail on the left with the app's name, the team as a chip (whose bill it lands on), the eight steps numbered (a check once passed, the current one filled), each with a one-line summary of what's chosen (the branch, the city, the parts, the variables, the database, the domain and alerts, secrets left), and the price a month at the bottom, counted up as choices change (estimated from the instance sizes before pricing; DigitalOcean's own after; "plus the cluster's own bill" with a managed cluster). The right side shows STEP N OF 8, a headline and a sentence, the step, and a footer with Cancel, Back and Next. Steps slide in from the side they come from (they fade under Reduce Motion); earlier steps can be jumped to from the rail, Secrets and Review only once priced.
  1. Source: the app's name (editable only for a new app); for git-hosted parts the host and repository, Branch (with Use <checked-out branch> when they differ) and Deploy when I push, with notes for unpushed commits and uncommitted changes; for images, Built on this Mac.
  2. Region: App Platform's ten regions as cards with a globe for their side of the world, the one nearest the Mac's time zone marked (Africa goes to Amsterdam, South America to New York); a live app's region is locked, with a note that Dante doesn't move a running app.
  3. Components: a card per part with its price a month: Size (a menu of shared and dedicated CPU sizes with prices), Copies (Fixed with a count, or Scale by CPU with at least, at most and the CPU to aim for; choosing it on a shared size moves to the cheapest dedicated size with as much memory), Port and Health check for services, and Run. Static sites say they're on the CDN and free.
  4. Variables: per part, name and value rows; a secret says it's asked for at deploy; a variable bound to a database, or a secret the deploy will bind (`DATABASE_URL`, `POSTGRES_PASSWORD`…), shows "from the db database"; Add, a lock to make one a secret, and remove.
  5.   6.   7. Secrets: while checking, a spinner and what's happening; a failure in red with Try again; otherwise the database's variables as green rows and a field per SECRET without a value that DigitalOcean doesn't already hold, Fill N from .env, the .env tag and warning, and how many are left. Continue (Return) prices it; with nothing to fill it says so.
  8. Review: chips for the app, region and team; the route drawn like the Infra view, with pulses moving along dashed links from where the code comes from (the git host and branch, or This Mac's Docker build into the registry, marked new and free or full) to App Platform in the region; What runs, a tile per component (kind, size, copies or a scaling range, its price or Free, its folder) and per database; notes for the team's bill, unpushed and uncommitted work, a registry to make, and a full registry in red (Deploy stays off). Deploy has no keyboard shortcut.
- Deploying: the step (checking the spec, making the registry, building or pushing each image, sending the spec, DigitalOcean deploying) with Show the build output; a failure in red with Try again, Ask the agent to fix it and, when App Platform can't read the repository, Let App Platform read the repository.
- The live app: its address (opens the site), the current deployment's state with a pulsing dot while it runs, the region and who's signed in; while deploying, its steps as chips joined by a line (done, running, failed); a failed deployment's step and reason with Ask the agent to fix it; the last deployments with their state, cause, commit and age (Live marked), All N deployments.
- Components: each with its health dot, kind, replicas ready, size, CPU and memory now with a sparkline of the last hour, and restarts today in amber; services and workers of a live app have Console.
- Getting in (under the live app, or under the plan before the first deploy): an icon for the way it signs people in and a sentence ("Requests need an API key (Authorization: Bearer <key>). - Logs: Build, Deploy or Runtime for every component or one, loaded on Load (runtime from the live deployment's stream, the last thousand lines; build and deploy from the latest), and a sentence when there's nothing yet.
- Security and recommendations: a line counting security findings and recommendations (green when there's nothing to fix), then Security and Recommendations groups and tips behind Show tips; each row has a severity, title, where, why it matters and the fix, and its area (secrets, network and HTTPS, image, reliability, monitoring, cost, data); a line saying what was checked.

## Actions
- Sign in with DigitalOcean: Dante registers itself once per Mac as a public client (no secret exists) with the exact loopback address `http://127.0.0.1:<port>/callback` (DigitalOcean redirects to the registered address exactly, port included), listens on that port again on later sign-ins and updates the registration only when the port is taken, opens DigitalOcean's authorize page in the default browser with PKCE, takes the reply on a one-shot listener, and keeps the refresh token in the Keychain; access tokens live in memory for their hour. Signed in as <name · team> with Sign out sits under the plan, and Sign out is in the … menu once an app is linked; signing out revokes the token and forgets it.
- Write .do/app.yaml: writes the plan with a header saying what the file is, and opens it. Never overwrites an existing file.
- Deploy… / Deploy again…: opens the wizard on `.do/app.yaml` (or, before there is one, on the plan Dante would write) and loads the sizes and the team's database clusters. Leaving step 6 writes the choices into the file only when they changed (the header comment, the order and every key the wizard doesn't know stay; comments inside the body are lost), then works out what to build and which secrets are missing and prices it. Going back to an earlier step drops the pricing. Deploy then makes the registry if needed, builds and pushes the images (tagged with the commit, plus the time when there are uncommitted changes), creates or updates the app, links it to the project, and watches it every five seconds until it's live or failed, with a notification when Dante isn't in front.
- Fill N from .env: copies the needed secrets' values from `.env` and `.env.local` at the root and in each component's folder (the component's own win), over what mise sets there, leaving out placeholders (empty, `$…`, `<…>`, changeme, xxx, todo, secret, password, your…). Each filled row is tagged .env until edited, and an amber note says these are development values and production needs its own, above all encryption and signing keys. Nothing is sent until Deploy.
- Console: opens a shell inside the running component in a terminal tab of its own ("<component> on DigitalOcean"), like DigitalOcean's Console and `doctl apps console`: Dante asks the API for the console's WebSocket address (scope app:access_console), writes it to a one-use 0600 file and runs the bundled `dante do-console <file>`, which reads and removes it, so the address's token is never on a command line or in the shell's history. Keystrokes go up raw, the terminal's size follows the tab, and exit or ⌃D closes it. A sign-in made before Dante asked for the console says so, with Sign in again.
- Getting in: Run in Console opens the component's console and types the step's command once the shell answers (you press Return); Run here runs a local step in a terminal tab of its own, in its folder; Save as .dante/access.yaml writes the guess to the repo to correct by hand; Ask the agent to write it (or check it) sends what Dante found and the file's format, asking it to prefer steps that work on the deployed app and never put a key in the file.
- Resize…: the wizard on that component's Components step only; Save and price writes the size into `.do/app.yaml` and goes on to pricing and review. Deploying updates the app in place: the database and its data stay.
- Explore in Data: asks the running app (through its console, like Console) for the variables bound to the database (`${db.DATABASE_URL}`, or host, user, password and name), adds "<db> on DigitalOcean" to Local › Data read-only with the password in the Keychain, and opens it.
- Back up now: the same connection, then `pg_dump` (custom format, no owners or grants) to Application Support/Dante/backups/<app>/<db>-<date>.dump on this Mac (0600), never the repository.
- Restore… (a backup on this Mac): confirmed; backs up what's there first, then `pg_restore --clean --if-exists --single-transaction`, so a failure changes nothing.
- Start fresh… (dev database): type its name to confirm; backs it up, then drops the tables, views, sequences, routines and types the app's user owns in the public schema (keeping the schema and its grants), and says to deploy again so the migrations make them.
- Restore to a new cluster… (managed): confirmed with the monthly list price; DigitalOcean makes `<cluster>-restored-<MMdd-HHmm>` from the backup; the app keeps the old cluster until it's switched in Deploy again › Database.
- Resize (managed): a size from the menu, confirmed with its price; DigitalOcean moves the cluster in place with a short blip (needs `database:update`, asked for at sign-in).
- Use an existing app: links one of the account's apps to the project (kept per project on this Mac).
- Cancel deployment, Roll back to this (asks first), Refresh, and the … menu: Open in DigitalOcean, Unlink from this project, Delete app… (asks first, saying it can't be undone).
- Ask the agent to fix these / it: sends the findings, or the failure with the end of its log, to the agent in charge, who changes only the repo and never deploys.

## States
- No app found in the code: says so and suggests asking the agent for a Dockerfile.
- `.do/app.yaml` that can't be read: says which part is wrong, in red.
- The linked app was deleted elsewhere: the link is forgotten and the page says so.
- The sign-in is no longer accepted: back to the sign-in card.
- The sign-in lacks a scope DigitalOcean asked for ("missing database create permission", from a sign-in made before Dante asked for it): the Deploying card says so in words with Sign in again, which signs out and back in and keeps the linked app; Ask the agent isn't offered, since the repo isn't at fault.
- Signed out: the plan and the checks of the file and Dockerfiles still show.

## Edge cases
- App Platform builds static sites only from git; built here, a static site is served by nginx as a small service instead, which costs like one.
- Built here, all components share one registry repository named after the app, with a tag per component, because the free registry plan holds one repository. The registry is made in the region nearest the app's.
- The images are built for linux/amd64 whatever this Mac is. The push signs in with credentials that expire in half an hour, written to a Docker config in a folder of its own that's removed straight after; the person's own Docker config is never touched.
- A Dockerfile Dante writes for a static site is passed to the build only, never written into the project, and drops dot files (.env, .git) in a stage that isn't pushed.
- A spec with a database: variables naming the database's password, user, host, port, name, URL or CA (`POSTGRES_PASSWORD`, `PGHOST`, `DATABASE_URL`, `DB_USER`…) are bound to it (`${db.PASSWORD}` and friends) when the plan is written and again when the sheet opens, so they're never asked for; `DATABASE_URL` is added. With several databases, Postgres wins.
- Secrets: the file holds SECRET variables without values. Typed values are sent once and not saved; on a later deploy DigitalOcean's encrypted value is sent back unchanged. A value written into the file is a critical finding.
- An update whose spec didn't change starts a deployment of what's pushed, so Deploy again always deploys.
- Creating or updating an app waits up to two minutes for DigitalOcean (pricing 90 seconds, everything else 30). When creating times out, the app may still have been made, so Dante looks for an app with the spec's name for a minute and links it rather than making a second; only when none appears does it say to try again.
- Let App Platform read the repository is offered only when the failure is about reading the repository, not for every message that names git or DigitalOcean.
- A Dockerfile builds from the context compose gives it (`build: {context: ./Code, dockerfile: api/Dockerfile}`), else from the folder above when its COPY lines name its own folder (`COPY api/go.mod ./`), else its own folder; folders such an image copies in (an admin site the API embeds) aren't made components of their own.
- When the project's repository is a folder inside it (docs beside a `Code/` repo), `.do/app.yaml` names folders from the project (`Code/api`) and Dante sends git-hosted components' `source_dir` and `dockerfile_path` as App Platform sees the cloned repository (`api`); images built here keep the project's paths.
- An app that has never gone live shows its newest deployment's steps and failure; logs are shown without the builder's colour codes.
- A dev database's user gets its rights on the public schema only when a deployment completes, so a PRE_DEPLOY job (migrations) on a new dev database fails with "permission denied for schema public": Security and recommendations flags it (high) and says to make it POST_DEPLOY until the first deployment is live, and to rename a dev database a failed deployment made. DigitalOcean refuses adding one database and removing another in one deploy; the Deploying card says to keep the old one for this deploy and remove it in the next.
- A job run before or after each deploy shows as "Job · before each deploy" with no monthly price, and isn't counted in the estimate.
- Pricing swaps images not yet built for a stand-in, so the size is priced before anything is built.
- Requests only go to api.digitalocean.com and DigitalOcean's sign-in, without following redirects; logs come from the signed links the API gives. The live site is asked only for its own headers.

- The wizard won't go on while a choice can't work, and says why in red in the footer: a name that isn't lowercase letters, digits and dashes; scaling by CPU on a shared size; a scaling range that runs backwards; a port outside 1–65535; a health check path without a leading slash; a repeated or badly named variable; a managed database without a cluster; a domain that isn't one.
- Autoscaling writes `autoscaling` (min, max and the CPU percent) and drops `instance_count`; the estimate counts the smallest number of copies. Alerts the wizard doesn't offer (and other keys) are kept as they were.
- `DANTE_DEPLOY_DEMO=1` (debug builds) opens the wizard with made-up sizes, a made-up cluster and team and no network, and its Deploy closes the wizard without doing anything, for checking its design.

- A step whose command needs `{url}` can't run before the app has an address; Run in Console is off until the app is live.
- Nothing in the code about getting in: the card shows only on a live app, saying so, with Ask the agent to write it.

- Database work needs the app running (Dante reaches the database through it) and pg_dump, pg_restore or psql on this Mac (found on PATH, Homebrew's libpq or Postgres.app); when missing, the card says to install with `brew install libpq`, typed by you. An older pg_dump than the server, or a managed cluster whose trusted sources leave this Mac out, is explained in words.
- No running part of the app has the database's address: the card says to bind DATABASE_URL to `${db.DATABASE_URL}` in a service and deploy again. An image without a shell can't be asked, and says so.
- The connection's password is used for one command (in PGPASSWORD, never on a command line) and, for Explore in Data, kept in the Keychain; it's never shown.
- A sign-in made before `database:update` was asked for gets "Sign out and sign in again" when resizing a cluster.
- `DANTE_DEPLOY_DEMO=live` (debug builds) shows the page as for a running app with a dev database and a managed cluster with two daily backups, made up and without network.

## Acceptance
- Back up now on a running app with DATABASE_URL bound writes a .dump file on this Mac that `pg_restore --list` reads; Restore puts it back after making a before-restore backup.
- Nothing that changes a database runs without a confirmation, and Start fresh needs the database's name typed.
- A project whose server reads an Authorization header shows Getting in saying it needs an API key, and a project with `.dante/access.yaml` shows exactly the file's steps.
- Nothing is created, changed, deployed, rolled back or deleted on DigitalOcean without a button press, and the wizard only writes `.do/app.yaml` when you go past step 6, and creating, rolling back and deleting are confirmed with what they do; the deploy sheet shows the team and the price first.
- The sign-in is never on a command line, in a file or in an agent's environment, and Dante never reads doctl's config or the browser's cookies.
- A secret's value never goes into the repository or user defaults.
- With a Dockerfile and no git host, Write .do/app.yaml then Deploy builds, pushes and deploys the image, and the page shows the app live with its address.
