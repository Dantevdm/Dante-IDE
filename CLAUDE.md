# Dante: notes for Claude

Native macOS IDE in Swift 6 / SwiftUI, built with SwiftPM (no Xcode project). Design reference: https://claude.ai/artifact/KFxwBAj14jL7w1MHNcc5Pi (generated by `design/generate_screens.py`).

## Commands

- Build: `swift build`
- Test: `swift test` (Swift Testing: `import Testing`, `@Test`, `#expect`). With only the Command Line Tools (no Xcode), `swift test` stops at SwiftTerm's Metal shader; `scripts/kit-tests.sh` still runs the DanteKit tests. SwiftUI's macros need Xcode, so the app itself can't be built without it.
- Large-repo timings: `DANTE_BENCH=1 swift test -c release -Xswiftc -enable-testing --filter LargeRepoBenchmark` (a generated 50k-file repo; prints each whole-project pass)
- App bundle: `scripts/bundle.sh [debug] [--open]` → `build/Dante.app` (bundle id `dev.dante.ide`). It signs with the first Apple Development certificate (or `DANTE_SIGN_IDENTITY`), falling back to ad-hoc: an ad-hoc signature changes every build, so macOS would ask for the microphone, speech and Keychain again each time.
- Release: `scripts/release.sh <version>` → `build/Dante-<version>.dmg` (signs and notarises only when `DEVELOPER_ID` and `NOTARY_PROFILE` are set; otherwise ad-hoc). Build anything you publish from a checkout outside the home folder (`git worktree add /tmp/dante-release <tag>`): SwiftPM writes the build path, and so the user name, into the binary. The icon is drawn by `swift scripts/make_icon.swift` into `Resources/AppIcon.icns`.
- Open a folder on launch: `open build/Dante.app --args "$PWD"` (files after the folder open in tabs) (AppDelegate turns off `NSTreatUnknownArgumentsAsOpen`; otherwise AppKit treats the path as an open-file event and SwiftUI makes no window)

## Modules

- `DanteOpen` (Foundation only): `OpenRequest` parses the `dante` command's arguments (`file:line`, `-n`) into a `dante://open?path=…&line=…` URL and reads it back (file URLs too, from Finder and the Dock); `OpenTarget.plan` sends each folder to one window and each file to a requested folder, an open project, or its nearest `.git`/`.dante` folder. `DanteCLI` is the `dante-cli` product, bundled as `Contents/Resources/bin/dante`; it runs `open -a <its app> <url>`. In the app, `Opener` (from `RootView.onOpenURL`, with `handlesExternalEvents` so existing windows take the event) reuses the window with the folder, then a launch-screen window, then asks `openWindow` and queues the target for the new window's `onAppear`. `CommandLineTool` (DanteKit/System) gives Settings → Tools the `ln -sf` to type into the terminal.

- `DanteKit`: UI-free models. `@MainActor @Observable` classes, value types elsewhere. Must not import SwiftUI views.
- Fonts: Geist and Geist Mono (OFL, `DanteEditor/Resources/Fonts`) are registered at launch by `DanteFonts`. Use `.font(.dante(size:weight:design:))` in views, never `.system(size:)`, and `DanteFonts.mono`/`sans` for AppKit; both fall back to the system fonts when `Preferences.usesGeist` is off.
- `DanteEditor`: the AppKit editor (`CodeEditorView` wraps a TextKit 2 `NSTextView`). Highlighters sit behind the `Highlighter` protocol: `TreeSitterHighlighter` (SwiftTreeSitter plus grammar packages for Swift, Python, JS, TS, Go, Rust and JSON, queries read from their resource bundles) with `RegexHighlighter` as the fallback. Keep grammar packages on tags that list `scanner.c` explicitly. Tokens are computed off the main thread. `Completion.swift` draws the completion list inside the editor's scroll view (child windows don't show in window captures); keys reach it through `doCommandBy`. Text changed outside the editor (reload, rename, format) is applied as one undoable edit of the differing range. `revealRange` scrolls with `CodeEditorView.center`, which lays out TextKit 2 up to the range and centres it without scrolling the gutter away.
- `DanteKit/Claude`: talks to Claude Code with `claude --input-format stream-json --output-format stream-json --permission-prompt-tool stdio` (the Agent SDK's wire protocol). `ClaudeEvent` parses output lines, `ClaudeInput` builds stdin messages, `ClaudeSession` keeps the transcript, and `ProposedChange` turns Edit/MultiEdit/Write calls into diffs. `Attachment` turns files into user-message content blocks (images resized to 1568px, PDFs as `document` blocks, Word/RTF/HTML via `textutil`, other binaries by path); `Session.claudeAttachments` holds them until the next `askClaude`. `InlineEdit` is ⌘I in the editor: the selection widened to whole lines, a prompt with the surrounding code, and the reply cleaned of fences; `InlineEditModel` (DanteApp) holds the proposal until accepted. `ClaudeSession.asksFirst` appends `ClaudeBrief.clarifyingQuestions` to the system prompt; AskUserQuestion calls arrive as permission requests and are answered with `answer(_:answers:)`, which returns the input with `answers` filled in. `ClaudeHistory` reads earlier conversations back from Claude Code's transcripts for the panel's history popover (`resume(conversation:items:)` continues one). Transcripts reach hundreds of MB, so `TranscriptScan` reads them as bytes (memchr/memmem); a line's own `"type"` often comes after `message`, so use `topLevelType`, never the first match. `ClaudeUsage` estimates the current five-hour window and the week from every local transcript (deduped by message id); `ClaudeAccount` keeps only the plan from `claude auth status`. Never read Claude Code's credentials or call its usage endpoint. `result.total_cost_usd` is a running total per process, not per turn. `TokenUsage` on assistant events drives the context meter in `ClaudeFooter`; `compact()` sends `/compact`. `onAttention` fires when a turn finishes or a tool waits for approval; `Session.notifyClaude` posts a notification when `Preferences.notifiesOnClaude` is on and Dante isn't active. Each turn keeps a `TurnCheckpoint` (`ClaudeSession.checkpoints`, keyed by the user item's id): `approve()` saves a file's text before Claude Code applies the edit, and `undoTurn` writes the originals back (deleting files the turn created) and tells Claude on the next message. Bash side effects aren't undone. `applyAll(restOfTurn:)` approves the waiting edits and, with `restOfTurn`, every edit until the turn ends (`ApplyAllBar` over the composer). `ComposerToken` finds the `@file` or `/command` being typed; `ComposerCommand` lists the built-in commands and one per skill; mentioned files are named to Claude in the message's context. `ClaudeSetup` backs the Setup area (`ClaudeAreaView`, `Session.Area.claude`): `ClaudeSkills` (SKILL.md front matter in `.claude/skills` and `~/.claude/skills`, `suggestions` from the project's files with a draft prompt each, a fortnightly `reviewDue`), `ClaudeMemoryFile` (CLAUDE.md files and their per-message token cost), `MCPServer.parse` (`claude mcp list`), `ClaudePlugin.parse` (`claude plugin list --json [--available]`, read leniently) and `ClaudePermissions`. Child processes must not inherit `CLAUDECODE`, or Claude Code refuses to start as a nested session. `ClaudeRules` reads `claude:` from `project.yaml`: `never` paths go to Claude Code as `--settings` deny rules and are also refused in `can_use_tool`; `flag` and out-of-`propose` edits get a `ruleNote` on the diff.

- Search by meaning (`DanteKit/Search/SemanticIndex.swift`, `SemanticState`, `MeaningSearchView`): `Chunker` cuts files at top-level declarations (doc comments included, long ones in overlapping windows), `SemanticIndex.build` embeds only pieces whose text hash is new with an embedding model in Ollama (`ModelRouting.embeddingModel`, `/api/embed`, vectors cut to 512 numbers and normalised), saving progress as it goes and main code first; the index is a binary plist per Mac in Application Support (`Dante/semantic`), never in the repo, and skips env files, lockfiles, data and `never` paths. `SemanticSearch` updates and queries it for the Search panel's Meaning mode, `dante search` and the MCP tool `search_code` (approved without asking; it stays on the Mac). Embedding runs at about six pieces a second, so a first index is a background job.
- `DanteKit/Search`: `ProjectSearch` scans the workspace's file index (no ripgrep dependency) with NSRegularExpression, using open dirty documents' text; columns are UTF-16. `ProjectReplace` re-matches the current text and replaces matches chosen by id (`line:column`). `SearchState` (DanteApp) debounces and keeps results per window; `Session+Search` does the replacing.
- `DanteKit/Project/GitRepository`: `GitStatus` (porcelain v1 `-z`), `GitBranch` (for-each-ref), `UnifiedDiff`, and the commands behind the Changes panel. Network commands never prompt (`GIT_TERMINAL_PROMPT=0`, ssh BatchMode); a `Failure` that needs credentials carries the `terminalCommand` to run instead. `ClaudeQuick` is a one-shot `claude -p --tools ""` for small jobs such as `CommitMessage`; `CommitMessage.read` splits a `WARNING:` line (or a reply that reads like prose) off the message, and `SecretScan` checks the diff's added lines first, so both commit boxes show a `CommitWarning`. `GitModel` (DanteApp, `Session.git`) is loaded from `WorkspaceView` on every revision. `GitBlame` blames the editor's text through `--contents`, so unsaved edits don't shift lines; the status bar shows the caret line's commit. Quote arguments typed into the terminal with `Shell.quote`. Merge conflicts: `MergeConflict` parses markers (diff3 bases too) and rebuilds the file from per-hunk `Choice`s, leaving unchosen hunks' markers exactly as they were; `GitRepository.diff3` re-merges the index stages with `--diff3` so `fillingBases` can add bases the working file lacks; `MergeOperation.detect` reads MERGE_HEAD, rebase-merge/ and friends (in a rebase "ours" is upstream, so `sides` names them). `ConflictView` replaces `DiffView` for conflicted files; Mark Resolved writes and stages, and Changes shows Continue/Abort while an operation is in progress. `ExplorerSelection` holds the explorer's multi-selection (Finder's click rules); Finder may hand over file reference URLs, so pass dropped and pasted URLs through `FileOperations.resolved`.
- `DanteKit/System/Shell`: `Shell.run` (drains both pipes) and `Shell.stream` (merged lines) for every external command, with the user's login-shell environment. A folder inside an open remote project's mirror runs the command on its host instead.
- `DanteKit/Remote` (docs/plans/remote-ssh.md): a remote project is a local mirror kept in step by `RemoteSync` (rsync over ssh; deletions only cross for files unchanged since the last sync, pushes only send files changed here, mass deletions are held back; the last sync's files and times are saved beside the mirror). `RemoteRegistry` maps open mirrors to hosts for `Shell`, `ClaudeSession` (runs `claude` on the host; `mirrorPaths`/`hostPaths` map tool-call paths) and the terminal; it also remembers known mirrors per Mac. `SSH` builds command lines (`BatchMode`, a shared `ControlMaster` started by `connect` with its output in a file, never a pipe); `DANTE_SSH` swaps in a stand-in, which the tests use to sync a local folder. `Session+Remote` attaches a sync when a mirror opens; the debugger is off for remote projects. `Shell` sends `extra` environment (passwords) to a host on stdin (`readingEnvironment`), never on the ssh command line. Compose and database clients run on the host (`DatabaseClient.route(projectRoot:)` can't check the host for a client, so it picks the compose service or the bare client name); running services' ports are forwarded here with `SSH.forward` (`RemoteSync.forwarded`/`unforwarded`), and the Env area skips this Mac's port checks. The host's Claude transcripts are copied to `RemoteProject.transcriptsURL` (`RemoteSync.pullTranscripts`, on opening and after each turn), where `ClaudeTranscripts.folder` and `ClaudeUsage` find them.

- Settings are a standard macOS `Settings` scene (`SettingsWindow`, Dante › Settings…, ⌘,) with toolbar tabs: appearance, editor, keyboard, languages, files, agents (who leads first, then Claude's model, settings for either agent, voice and cloud agents), tools (`Tool`/`ToolStatus` in `System/Toolchain`: versions and install commands, typed into the terminal but never run) and the project (move `.dante` to the Trash, set up again, forget saved connections). The Tools and Project panes act on `ActiveProject.shared.session`, the window that was main most recently. Explanations go in `.help` tooltips, not footers.
- Menu shortcuts come from `Shortcuts` (DanteKit/Settings: `KeyBinding`, the command list with defaults, overrides in user defaults); menus use `.shortcut("id")` and hints use `Shortcuts.label`, never a literal key. SwiftUI doesn't rebuild menus it has made, so `MenuShortcuts` (on `Shortcuts.onChange`) sets the changed `NSMenuItem` directly; its own items refuse the shortcut they were built with, so a reset to a default can need a restart (`needsRestart`, noted in Settings). The Keyboard pane records them; the Languages pane edits `LanguageServerOptions` per server (off, command, JSON sent as initializationOptions and answering `workspace/configuration`), and `LanguageServices.restart` applies them.
- `DanteKit/Settings/Preferences`: everything in the Settings window except theme and font size (`ThemeStore`), in user defaults; `Preferences.shared` is read directly by views and `Session`. `Session.save` tidies whitespace and writes now; `saveFormatting` (⌘S, Save All) formats first when asked; auto-save writes without tidying.

- Presence (`DanteKit/Presence`, `DanteApp/Views/Presence`): the menu bar orb. `Presence.combine` turns every window's `PresenceSource` (from `Session.presenceSource`) into one `PresenceMood`, most urgent first; `PresenceTracker` shows `done` for a moment after a turn; `OrbStyle` holds each mood's palette, energy, aura and lightning (idle cycles `idleForms`). `PresenceController` owns the status item and its popover (`PresencePanel`), and re-reads through `withObservationTracking` for every `OrbView` it has attached. `OrbView` is an MTKView drawing `OrbShader` (Metal source compiled at runtime, since SwiftPM doesn't build .metal files); it eases between styles and pauses when occluded. The orb has no eye (the user found it disturbing); don't add one back. `DANTE_ORB_SNAPSHOTS=<folder>` writes every mood as PNGs and quits. `Vitality` pushes the style (`OrbStyle.adjusted`): intensity from `WorkRate` (tool calls per minute plus what's running), fatigue from the five-hour window against the busiest one (`ClaudeUsage`, reloaded every two minutes), and sleep when the agent in charge is out (`ClaudeSession.outOfUsageSince`: Claude out with Codex leading isn't asleep); `PresenceModel.lead` is the frontmost project's agent, and `usage`/`usageReset` show Codex's own limit (`codexLimits`) or Claude's window against the busiest; fatigue drains the colours and dims it (`drowse`), and the orb nods off. `VoiceController` is push-to-talk: ⌃⌥Space (a Carbon hot key, no Accessibility needed) or the panel's Talk button, on-device `SFSpeechRecognizer`, sent after a pause; `VoiceCommand` picks out stop/yes/no/switch to, status, usage and thanks (`VoiceStatus` answers the middle two without a turn), the rest goes to Claude in the frontmost project. Replies are read as they stream (`SpokenStream`: code skipped, then "There's more on screen"), handed to the synthesiser in chunks by `SpeechQueue` (the first sentence at once, then what gathered while it played), in the voice and speed chosen in Settings. The natural voice (`NaturalVoice`, on by default once set up from Settings › Claude, `NaturalVoiceSetup`) is Kokoro through `kokoro-onnx` in Application Support/Dante/voice (its own venv; model files pinned by SHA-256); `NaturalSpeaker` keeps the server (`NaturalVoice.script`: JSON lines in, files of float samples out) warm for ten minutes, plays chunks back to back on one `AVAudioPlayerNode` and meters the mixer for the orb, and falls back to `AVSpeechSynthesizer` when it fails. Closures that audio, pipe or process threads call are made in `nonisolated static` functions: one written in a main-actor method traps off the main thread. `DANTE_VOICE_MUTE=1` runs it all in silence for testing; the orb pulses with each spoken word and the Stage shows the sentence being said. With `keepsConversation`, Dante listens again after it finishes speaking until silence or thanks. ## Conventions

- Colours come only from `Theme` tokens (`@Environment(\.theme)`), never literals in views. All three themes (Dark, Light, Paper) must look right.
- The window's system title bar is hidden; `TitleBar` draws its own and leaves room for the traffic lights.
- Menu commands reach the window's state via `@FocusedValue(\.session)`.
- `Section` is SwiftUI's; the workspace's areas are `Session.Area`.
- Every page and every view inside one has a spec file, `spec/pages/<id>.md` (format in spec/README.md: front matter with id, title and phrases, a spoken summary, then Highlights, Shows, Actions, States, Edge cases and Acceptance); `spec/places.yaml` is the rail. The `DanteSpec` target bundles the folder (found by `DanteSpec.folder`, never `Bundle.module`) and `PageSpec` reads it into `FeatureGuide`. Voice opens pages from it (`VoiceCommand.navigate`, "show me the infrastructure"; a view is asked for through `Session.areaView`, which the area also sets as it switches; `Session.show(_:)`), explains them ("what's on this page?") and lists them ("what can you do?"); the agents get it in their brief (`FeatureGuide.brief`) and through `dante mcp`'s `dante_pages` (the list or a page's spec) and `show_page` (the app opens the page as the call goes by, through `ClaudeSession.onDanteTool`), both approved without asking. Write or update the spec in the same change as the feature, as precisely as a port to another platform would need; `FeatureGuideTests` fails for an area without a file, an incomplete file or a failing case in `spec/fixtures/voice.yaml`, which every build must pass.
- Dante's own task list is `.dante/tasks.yaml` (a plain file now that the app has no board). Move a task's state when you finish it.
- Verify UI changes by running the bundled app, not just by compiling.
