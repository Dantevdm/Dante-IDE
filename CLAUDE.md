# Dante: notes for Claude

Native macOS IDE in Swift 6 / SwiftUI, built with SwiftPM (no Xcode project). Design reference: https://claude.ai/artifact/KFxwBAj14jL7w1MHNcc5Pi (generated by `design/generate_screens.py`).

## Commands

- Build: `swift build`
- Test: `swift test` (Swift Testing: `import Testing`, `@Test`, `#expect`)
- App bundle: `scripts/bundle.sh [debug] [--open]` → `build/Dante.app` (bundle id `dev.dante.ide`)
- Open a folder on launch: `open build/Dante.app --args "$PWD"` (files after the folder open in tabs) (AppDelegate turns off `NSTreatUnknownArgumentsAsOpen`; otherwise AppKit treats the path as an open-file event and SwiftUI makes no window)

## Modules

- `DanteKit`: UI-free models. `@MainActor @Observable` classes, value types elsewhere. Must not import SwiftUI views.
- `DanteEditor`: the AppKit editor (`CodeEditorView` wraps a TextKit 2 `NSTextView`). Highlighters sit behind the `Highlighter` protocol: `TreeSitterHighlighter` (SwiftTreeSitter plus grammar packages for Swift, Python, JS, TS, Go, Rust and JSON, queries read from their resource bundles) with `RegexHighlighter` as the fallback. Keep grammar packages on tags that list `scanner.c` explicitly. Tokens are computed off the main thread.
- `DanteKit/Claude`: talks to Claude Code with `claude --input-format stream-json --output-format stream-json --permission-prompt-tool stdio` (the Agent SDK's wire protocol). `ClaudeEvent` parses output lines, `ClaudeInput` builds stdin messages, `ClaudeSession` keeps the transcript, and `ProposedChange` turns Edit/MultiEdit/Write calls into diffs. `Attachment` turns files into user-message content blocks (images resized to 1568px, PDFs as `document` blocks, Word/RTF/HTML via `textutil`, other binaries by path); `Session.claudeAttachments` holds them until the next `askClaude`. `ClaudeSession.asksFirst` appends `ClaudeBrief.clarifyingQuestions` to the system prompt; AskUserQuestion calls arrive as permission requests and are answered with `answer(_:answers:)`, which returns the input with `answers` filled in. Child processes must not inherit `CLAUDECODE`, or Claude Code refuses to start as a nested session. `ClaudeRules` reads `claude:` from `project.yaml`: `never` paths go to Claude Code as `--settings` deny rules and are also refused in `can_use_tool`; `flag` and out-of-`propose` edits get a `ruleNote` on the diff.
- `DanteKit/Plan`: `LifecycleTemplate` (app, infra, apple, data: phases, starting checklists, detection from file paths; `Workspace.setUp` writes `.dante/` from one). `ProjectProfile.detect` guesses stack, template, stage and secrets for a project without a spec; `ProjectSetupRequest` builds the prompt from the parts ticked in `SetupSheet`, which `Session.offerSetup` shows on open. `.dante/tasks.yaml` (`TaskBoard`, via Yams) and `.dante/phases/<phase>.md` (`PhaseDoc`, plain markdown checklists). `Workspace.reloadSpec()` re-reads all of `.dante/`; the file watcher calls it on any change there. Edits to `project.yaml` are made line by line (`Lifecycle.settingCurrent`) so comments survive.
- `DanteKit/LSP`: `LSPFraming` (Content-Length JSON-RPC), `LSPClient` (one server process: initialize, full-text didOpen/didChange, publishDiagnostics, definition), `LanguageServices` (per window, lazily starts the server in `LanguageServer.all` for a file's language; edits are debounced). Positions are UTF-16, like NSString; convert many with `LineIndex`.
- `DanteKit/Search`: `ProjectSearch` scans the workspace's file index (no ripgrep dependency) with NSRegularExpression; columns are UTF-16. `SearchState` (DanteApp) debounces and keeps results per window.
- `DanteKit/System/Shell`: `Shell.run` (drains both pipes) and `Shell.stream` (merged lines) for every external command, with the user's login-shell environment.
- Area data, one folder each in `DanteKit`: `Docs` (`MarkdownDocument`, `Mermaid`: a parser for the flowchart, sequence and ER subset, drawn by `MermaidView` in the app rather than mermaid.js). `DocLibrary` also lists PDFs, images and Word files, but only under docs/, documentation/ and .dante/; elsewhere they're app assets, `Testing` (`TestCommand`, `TestOutputParser`, xUnit), `Environments` (`ComposeFile`, `ContainerState`), `Map` (`ArchitectureGraph`), `Release` (`ReleaseDraft`, `CIRun`), `Operate` (`HealthMonitor`, `ErrorDigest`, `LogWatch`). `Project/ProjectInfo` reads the rest of `project.yaml` (`test:`, `operate:`). Keep parsers pure and tested.
- `DanteApp`: the SwiftUI app. `Session` holds per-window state, including terminal tabs and back/forward history (`Session.Place` in a `NavigationHistory`, recorded from `onChange(of: session.place)`); `ThemeStore` is app-wide. Area screens live in `Views/Areas` and are built from the shared pieces in `AreaPage.swift` (`AreaPage`, `Card`, `RowList`, `EmptyState`, `CardGrid`, `Chip`, `LinkButton`). Views reload with `.task(id: workspace.revision)`.

## Conventions

- Colours come only from `Theme` tokens (`@Environment(\.theme)`), never literals in views. All three themes (Dark, Light, Paper) must look right.
- The window's system title bar is hidden; `TitleBar` draws its own and leaves room for the traffic lights.
- Menu commands reach the window's state via `@FocusedValue(\.session)`.
- `Section` is SwiftUI's; the workspace's areas are `Session.Area`.
- Dante plans itself: real tasks live in `.dante/tasks.yaml`. Move a task's state when you finish it.
- Verify UI changes by running the bundled app, not just by compiling.
